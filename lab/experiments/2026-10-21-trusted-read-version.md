# 读取版本绑定 Agent 表格写入

日期：2026-10-21。实现冻结提交：84985c6984740dd744bc04866cb763680d72daa3。

## 结论

实验快照的 company.table.write 现在把当前 run 的真实读取版本传入已有 OpenGate 乐观校验。诊断中，读取后发生的中间写入得到保留：旧版本被拒绝，远端调用次数不增加；显式使用新读取版本后才成功。缺少读取不能靠模型填写版本绕过。

这是局部合同修复，不是模型质量提升或跨库原子性修复。清空接口尚未接入同等前置版本检查，生产平台未部署。

## 实现

- ToolContext 增加默认空的 expected_table_version，不改变模型工具 schema。
- Phase2Nodes 在派发 company.table.write 时覆盖该上下文字段，只从当前 run 的 tool_results 获取最近一次匹配 tid 的成功 company.table.read 回执。核对回执 tool_name、tid，以及非布尔的非负整数 table_version。
- 同表写入/清空尝试、读取失败或读取回执缺失/无效，会让旧版本失效。再次写入前必须重新读取。其他表读取不会替换目标表版本。
- 原表格适配器仍先校验身份、权限及参数。没有可信版本抛出 TABLE_READ_REQUIRED；有版本则传给原 upsert_table_cells 的 expected_table_version。原 TableWriteConflict 转为带原错误码的 ToolExecutionError，workspace 适配器保留类型；冲突与未知结果区分。
- 模型指令补充先读后写、写后重读、冲突后重新核对意图。该指令辅助模型选择；强制校验发生在可信代码中。

冲突代码表示该次 upsert 在远端写入前被拒绝；不自动替模型刷新版本并重发。执行图可以让模型重新读取并核对，仍受已有工具轮数限制。

## 边界与后续

- 整表版本会因其他单元格变化而冲突，比逐单元格校验更保守；未证明模型能正确处理冲突后的业务意图，也未测额外读取成本。
- 当前版本来自 Django 审计；绕过审计的远端修改，以及远端提交但本地审计回滚的情形，无法靠该版本可靠检测。跨库原子性、业务端幂等、跨 run 防重仍未解决。
- 当前 run 的工具回执必须保留；裁剪回执会拒绝写入并要求重读。没有跨会话读取授权缓存。
- 权限/内容审核为允许夹具，远端为独立 SQLite；真实 Django ORM 与源码方法被执行，但不等于平台 IAM、真实 immudb 或 PostgreSQL 锁验证。
- 本轮只处理 company.table.write；clear_cells、自定义工具和其他直接服务调用不因此获得同等保护。

下一步优先补齐清空接口的版本校验，并在隔离的真实 PostgreSQL/immudb 环境验证并发与丢回执；之后才评估模型冲突恢复质量。生产部署前仍需要独立集成验证。
